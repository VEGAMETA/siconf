# Языковая модель: llama.cpp + Gemma 4 26B

## Выбор модели

Под 16 GB видеопамяти и 64 GB RAM. Сравнивали две модели:

| | Gemma 4 26B-A4B (QAT q4_0) | gpt-oss-20b (MXFP4, high) |
|---|---|---|
| Архитектура | MoE, 26B всего / ~4B активных | MoE, 21B / ~3.6B активных |
| GSM8K (50) | 49/50 | 48/50 |
| IFEval (50) | 46/50 | 37/50 |
| MMLU-Pro (112 / 56) | 81,3% | 50% (21 пустой ответ из 56) |
| Русский | хороший | слабый |

Победила Gemma, gpt-oss удалена. Подробности — [09-benchmarks.md](09-benchmarks.md).

## llama.cpp

- Сборка **b11852**, `win-cuda-13.4-x64` + cudart, лежит в `D:\llm\llama.cpp`.
- Режим маршрутизатора: `--models-preset models.ini --models-max 1`, адрес 127.0.0.1:8080. Модель грузится по первому запросу, в видеопамяти одновременно не больше одной.
- Файлы модели: `google/gemma-4-26B-A4B-it-qat-q4_0-gguf` (14,4 GB) + `mmproj` (1,2 GB), путь `D:\llm\models\gemma-4-26b-a4b`.

### models.ini — почему так

| Параметр | Значение | Зачем |
|---|---|---|
| `jinja`, `flash-attn on` | — | шаблон чата Gemma 4 и быстрое внимание |
| `fit = on` | — | llama.cpp сам решает, какую часть экспертов MoE держать в RAM, чтобы модель и контекст влезли в 16 GB |
| `cache-type-k/v = q8_0` | — | KV-кэш вдвое меньше почти без потерь |
| `n-predict = 32768` | — | страховка от зацикливания (размышления ограничивает посредник) |
| `c = 262144` | 256K | максимум модели; один вариант на всё |
| `no-mmproj-offload = true` | — | модуль зрения на CPU: +1,2 GB видеопамяти экспертам |
| `temp 1.0, top-p 0.95, top-k 64` | — | официальные параметры Google |

Размышления Gemma 4 включаются меткой `<|think|>` в начале системного промпта.

### Замеры скорости

Замер `scripts/speed.py`: генерация — 3 ответа по 600 токенов, чтение — ввод ~18 тыс. токенов.

| Конфигурация | Генерация | Чтение 18K | Документ 59K |
|---|---|---|---|
| 128K, зрение на GPU | 63,4 ток/с | 1515 ток/с | — |
| 128K, зрение на CPU | **69,4 ток/с** | **1869 ток/с** | — |
| 256K, зрение на GPU | ~41 ток/с | — | ~56 с |
| **256K, зрение на CPU (сейчас)** | **59,6 ток/с** | 1350 ток/с | 55,6 с |

- Зрение на CPU дало +9% к генерации при 128K и +45% при 256K: освободившаяся видеопамять ушла под экспертов. Плата за это — разбор одной картинки около 12 с вместо почти мгновенного.
- Очень длинный документ от этого не ускоряется: там узкое место — внимание, а не эксперты в RAM.
- Выгружать и загружать зрение по требованию нельзя: llama.cpp решает это при загрузке, а переключение режимов стоило бы перезагрузки модели и потери кэша беседы.
- Можно ускорить разбор картинок через `--image-max-tokens` (сейчас ~510 токенов на картинку), но мелкий текст на скриншотах будет читаться хуже. Не замерено.

### Параллельность

Сервер держит 4 слота. 4 одновременных запроса дают в сумме ~100 ток/с, по ~25 на каждый. Это выгоднее, чем по одному: генерация упирается в чтение весов из памяти, и одно чтение обслуживает сразу несколько ответов. Для MoE с экспертами в RAM выигрыш меньше идеального.

## Другие бэкенды

Open WebUI подключается к любому OpenAI-совместимому серверу. Для одного пользователя с 16 GB и экспертами в RAM llama.cpp — лучший выбор. Если появятся 128 GB RAM и модель на 100B+, стоит замерить **ik_llama.cpp**: он быстрее на гибридном MoE. vLLM и SGLang рассчитаны на серверы и только видеопамять. TabbyAPI (ExLlamaV3) требует, чтобы модель целиком влезла в видеопамять.

llama.cpp b11852 отвечает и в формате Anthropic (`/v1/messages`), так что Claude Code можно запустить на локальной модели через `ANTHROPIC_BASE_URL`. Но для агентной работы Gemma слишком слаба.
